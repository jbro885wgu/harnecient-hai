# 🎓 Teaching the hai-model: how to train your own (2026-11-22)

📅 Who this is for: you, or anyone who wants to make a hai-model their own.
Status legend: **BUILT**, **DESIGN**, **NOT YET** (see `0.hai-model-architecture.md`).

## 0. The one idea

A hai-model learns by **adding rows and counting outcomes**. It does not
change its code, and it does not run any training loop. So "training your own"
means three things you can do with plain text files:

1. **Teach it words and answers** (add concept and reply rows). BUILT.
2. **Tell it whether an answer was good** (grades 0 to 4, and RL scores from
   checks). Grades and RL weights are DESIGN.
3. **Show it material to learn from** (linked documents, and output from other
   models that you choose to watch). DESIGN.

Every one of these leaves a row, so you can always see what it learned and why.

## 1. Teach it new words and answers (BUILT, by hand)

Open `chat/data/concepts.pdl` in any text editor. A concept row is:

```
CONCEPT | <id> | <words, comma separated> | <reply id> | <label shown in options>
```

Example. To teach it about the nav system:

```
CONCEPT | nav | nav,navigate,page,pages,navigation | r_nav | nav
```

`nav` is the id. The words are what you type that should match it. The reply id
points at a row in `replies.pdl`. The label is what it shows when it offers
options.

Then add the reply, in `chat/data/replies.pdl`:

```
REPLY | r_nav | Navigation lives in the menu. Full nav comes with the window.
```

Rules that keep it working:

- **Use lowercase words**, one per token. Matching is on single words, not phrases.
  `pages` matches; `open page` does not match as one thing (it matches `open`
  and `page` separately).
- **Give every concept a reply id that exists.** A missing reply falls back to
  "I don't know that yet."
- **Use a new id for a new concept.** Renaming one breaks any ledger rows that
  name it.
- **Check it.** Run `./ops/hai chat/data <a fresh ledger>` and type your new word.
  The reply you wrote should appear. Then run the harness case (the repo's
  `cases/hai_chat.pdl`) to confirm nothing else changed.

To change how it moves between states, edit `chat/data/states.pdl`. Rows are
checked **top to bottom, first match wins**, so put the specific rows first and
the `*` (any concept) rows last. Actions: `none`, or `store_name` (the first
word you type becomes the name).

## 2. Tell it an answer was good or bad (DESIGN: grades 0 to 4)

Planned, not built. This is how it will work:

| Grade | Meaning | What it adds (RULE rows, to tune) |
|---|---|---|
| 0 | bad | one punish for the reply you graded |
| 1 | good | one reward |
| 2 to 4 | better | one reward plus a bonus that grows with the grade |

Stored in 3 bits, so values 5 to 7 stay free for later. The weight of a reply is
the Laplace ratio `(reward+1)/(reward+punish+2)`, the same formula the house's
harness bank uses. A reply the user keeps grading well rises in the ranking; a
bad one sinks, but is never deleted (the ledger keeps it).

Caps: a user's grades count at most a set number per day (RULE row), so one
person repeating a grade cannot make a reply dominant.

## 3. RL scores: learning from checks (DESIGN, the strongest signal)

The house already has a harness verdict: a case PASSes or FAILs, and a bank
weight counts those. The plan is to use the same thing for hai:

- A **tool call** (for example `open_page`) is a small op. Its outcome is judged
  by a harness case, not by you.
- A PASS gives it a reward row; a FAIL gives a punish row.
- A tool is only fired when its weight is above a threshold (RULE row).

This is the most trustworthy source, because a measured check is not a mood.
It cannot be built until tool calls exist (milestone M4).

## 4. Show it material (DESIGN)

### 4a. Linked documents (the user links a document, it learns at once)

Planned flow:

1. You link a text file or a markdown file (no code, no links fetched by hai).
2. hai splits it into sentences and writes rows tagged `SOURCE|<doc id>|<user>|<time>`.
3. Concept and reply rows from the document are active straight away: no
   training run.
4. Unlinking removes those rows through a verb, never by hand.

A document can add concepts and replies. It cannot change a tool's weight
directly. Size is capped by a RULE row.

### 4b. Observing other models (DESIGN, optional)

hai does not call another model's API inside a test. Instead an **adapter**
reads a text file that another model wrote (for example a report it dumped),
and writes **candidate** rows:

```
CANDIDATE | <concept or reply id> | <what it suggests> | SOURCE|<model name>|<file>|<time> | weight 0.5 (capped)
```

A candidate starts with a capped weight. It only becomes a real row after a
person confirms it or a harness verdict passes it. Nothing is promoted
automatically.

### 4c. Distillation (optional, never required)

Some people will want to use a larger model to write example answers. That is
allowed as one more source, under two rules:

- The outside model writes **fixed-shape rows** (one concept, one reply), never
  free prose that goes straight in.
- Only rows that a harness **verified** become part of the model. Everything else
  stays out.

The hai-model must keep working with zero outside models. If an outside model
disappears, nothing breaks; only the candidate queue gets shorter.

## 5. A checklist for training your own

1. Start a fresh ledger for each experiment, so runs do not mix.
2. Add concepts and replies by hand (section 1). Check each one by typing it.
3. Run the harness case after every change. A change that turns it red is undone.
4. Once grades exist (section 2), grade a few replies honestly, including the
   bad ones. A model trained only on good grades learns nothing about what fails.
5. Keep a note of what you taught it, and why. The rows already say what; your
   note says why.
6. Never hand-edit a ledger. Add rows through the verbs, or start a new ledger.

## 6. What it will not do (say these when you share it)

- It will not invent a new answer no one wrote.
- It will not get better at things you never taught it or linked to it.
- Its weights are counts. They show what happened, not what is true.
- An observed model's output is a suggestion until a person or a check confirms it.
