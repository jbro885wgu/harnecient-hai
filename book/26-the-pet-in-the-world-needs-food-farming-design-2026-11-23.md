## 2. The loop the owner described (DESIGN)
```
hungry  -> does it hold food?        yes -> eat            (hunger down)
        -> is there food on the page? yes -> walk to it, take it, eat
        -> neither: plant a seed -> water it -> (time passes: growth events) -> harvest -> eat
        later: ingredients -> cook (a recipe) -> better food
```
Every step is a **verb** that writes a ledger row, so the user can watch the pet learn to do the loop, and a person can do each step by hand.

## 3. Concepts, meanings, weights, events (what is pre-programmed)
- **Concept entities** (data, in the same bank format hai already uses): `food`, `seed`, `water`, `soil`, `plant`, `fruit`, `ingredient`, `meal`, each with **meanings** (words that point at them: "eat", "hungry", "apple") and **weights** (how strongly a meaning ties to a concept, moved by grades, as for every other word).
- **Created entities:** a verb can mint an entity (a seed, a plant on a cell, food in the inventory). The creation is a ledger row; the entity's kind is a concept.
- **Events** (clock rows, shipped on or off by data): `hunger_tick` (needs rise), `grow_tick` (a planted cell advances a stage if watered, a dry one does not), `dry_tick` (water level falls). Stages and rates are rows, never code constants.
- **Off switch:** `needs.pdl` rates of 0 (or an `ENABLED | 0` row) = no hunger, so the pet is just a chat toy in a world. The user can turn it off, as the owner asked.

## 4. The hybrid (answer to "what is wrong with the needs op")
The op is not broken; it is gated (quarantine, owner lifts per book), tied to an item ledger, native only, and its store is a file. **Reuse its DATA FORMATS and its rules; do not fork a second format.** One small core, C and JS, reads the same `needs.pdl`, `itemdata.pdl`, `recipes.pdl` shapes, with items and needs derived from ledger rows. **`survivor_op` is the test oracle:** a case runs both on the same inputs in a quarantined scratch copy and requires identical numbers; a mutant in either turns it red. Once the owner releases a hai-pal book from quarantine, an event page can call the real op on the desktop; the port serves the web and CLI-only users. Farming (section 2) is new rows and verbs in the same core; it is not in `survivor_op`, so it has no oracle and gets its own case with mutants.

## 7. Basic anatomy: digest, waste, breathe (owner 2026-11-23; DESIGN, built on what the house already decided)
**What the house already says (READ 2026-11-23):**
- **Owner principle 2026-10-25 (opt-in fidelity):** every system has a cheap default (a number that drifts, a need that ticks, tuning in a `.pdl`) and an optional detailed layer switched on per entity or case; behaviour lives in event pages, C ops only do what a page calls. The world rule `fidelity_max` sets the ceiling (`16.game/TERUMON-SHAPESHIFT-AND-EVOLUTION-TREES-DESIGN.md` section 5; `16.game/RPG-SPACE-COLLISION-AND-DESTRUCTION-DESIGN.md` section 4b).
- **A body plan is an anatomy part tree** (bones, muscle, lungs, brain ...); parts decide behaviour (wings enable flight) and **needs (air, food) follow the parts**. That is the `part_tree_lint` / "anatomy v0" roadmap item; the linter for any `NODE` tree, `&.widgits/_shared-lib/ops/tree_lint.c`, is BUILT (harness `tree_lint.pal`, 53 checks, 0 failing).
- **NOT FOUND / NOT BUILT:** an anatomy generator, a reaction resolver, a molecular view (`16.game/RPG-DUST-DESIGN.md` says so). The anatomy docs I found are designs, not code.
**For the pet (DESIGN):**
- **Cheap default (first version):** the needs of section 3 (hunger, plus a `waste` level that rises when it eats and falls when it "goes", and a `breath`/energy level that is always fine on land). Just numbers with rates in a `.pdl`.
- **Opt-in body layer (later):** a small part tree per pet as `NODE` rows (`mouth`, `stomach`, `gut`, `lungs`, `heart`, `brain`), checked by `tree_lint`. Eating moves a food item mouth to stomach to gut over `digest` events (minutes of game time), producing energy and then waste; `lungs` give breath; a missing or damaged part changes what the pet can do. Each stage is an event row; the part tree is data, so another game can swap in a different body.
- **Why it fits teaching:** "digest", "waste", "breathe" become concepts with meanings and weights like "eat", so the pet can be taught to use the right verb ("go" / "clean up") when its waste level is high, and a person can watch the chain in the Viz tab.
- **OPEN (owner):** (a) is waste visible in the world (an entity on the map the user can clean, which can feed a plant, closing the farm loop) or only a number? (b) does a sick or full-of-waste pet only get sad, or can it fall ill? (c) is the part-tree layer in the first web version or later? My defaults: visible waste entity that fertilises a plant; sad not ill; part tree later.

## 8. Body type: organic or robot (owner 2026-11-23: "we can try both at first"; DESIGN)
A body type is DATA, one file per type (`body_organic.pdl`, `body_robot.pdl`), chosen when the pet is born and recorded as a row; the same core, verbs and ledger serve both, so nothing is hard-coded per type (the opt-in fidelity rule of section 7). A type names: its **needs** (with rates), the **items that satisfy each need**, its **parts** (the optional part tree), and its **waste**.
| | organic | robot |
|---|---|---|
| main need | `hunger` (rises with time) | `battery` (falls with time and with moving) |
| what restores it | food items (`USE\|item\|eat\|hunger\|-40`) | power items (a charged cell, a charging pad entity, fuel) |
| second need | `waste` (rises when it eats, falls when it "goes") | `heat` (rises when it moves, falls when it rests) |
| third need | `breath` (fine on land by default) | `wear` (rises with use, falls with repair) |
| farm loop | seed, water, plant, harvest, eat | plant, harvest, **press into fuel** (a recipe), refuel; or place a solar panel entity |
| parts (later layer) | mouth, stomach, gut, lungs, heart, brain | power cell, motor, sensors, cooling, core |
| "cooking" | recipes make better food | recipes make better cells |
Both types share the teach loop, so "feed", "charge", "rest" are words the user teaches and grades. The needs of a type are rows, so a user can switch one off (rate 0) or switch every need off. The two types must give the SAME result for the same verbs on the shared parts (walk, pick up, create an entity); what differs is only which needs tick and what an item does when used. **Case:** one case runs the same script of verbs on an organic and a robot pet and checks the shared outcomes are equal and the type-specific ones differ in exactly the data-named way; a mutant that swaps the two files must turn it red.
**OPEN (owner):** (a) is the type chosen at birth only, or can a pet be rebuilt from one into the other (the terumon design has forms and shapeshift; a rebuild would be a row and a cost)? (b) do robots get a charging pad on the map for free, or must the user make one? (c) can the two types live in one session and share the farm? Defaults: chosen at birth only; the user makes the pad; yes, one shared world.

## 9. Cyborgs, and where this is going: a weight-adjustable, evolvable dustopia / terumon mini sim (owner 2026-11-23; DESIGN)
Owner: *"there can be cyborgs of course. It is supposed to eventually be a weight-adjustable, evolvable 'dustopia' learning, evolving 'terumon' mini sim."* The house already designed the two halves (READ 2026-11-23):
- **Terumon** (`16.game/TERUMON-SHAPESHIFT-AND-EVOLUTION-TREES-DESIGN.md`): one entity with a persistent identity (id, owner, level, EXP, skills, memories) **wearing one form**; a form is a node of an **evolution tree** naming a body plan, stat multipliers and a model. **Evolve** = unlock a form for good (earned, costs EXP and time, one way). **Shapeshift** = wear an unlocked form at will (costs MP, temporary, reverts at 0 MP). Care actions are skills that cost MP and give EXP (`@.apps/pet-trainer/skillbook.pdl`); looks change by stage and trait (`evolution.pdl`, op `pet_gen`). Cheap fidelity is the default (a form is a stat multiplier and a model); the deep layer swaps the anatomy part tree and needs follow the parts, under the world rule `fidelity_max`.
- **Dustopia** (`16.game/RPG-DUST-DESIGN.md`, `RPG-DUST-PETSLIKE-BOARD-DESIGN.md`): a scale ladder as data rows from a planet down to the molecular level, "limitless" generated menus by size, place and species; entities cook, harvest, create, do material science; anatomy and chemistry appear by zooming in. A seeded planet generator, an anatomy generator and a reaction resolver were NOT FOUND (design only).
**How a cyborg fits (DESIGN):** a cyborg is simply a body type whose data file carries BOTH need sets and BOTH item sets (`pet/data/body_cyborg.pdl`, BUILT as data, see section 10). In terumon terms a body type is a **form**; so `organic`, `robot`, `cyborg` are the first three nodes of an evolution tree, and "rebuild an organic into a cyborg" is an **evolve** row (earned, one way) while temporarily wearing another form is a **shapeshift** row (MP). The **weights** the owner wants adjustable are the per-need weights of section 10 (and later the concept weights the chat already learns); every adjustment is a ledger row, so a pet's whole evolution is replayable and a user can download and reopen it. **Evolution under learning** (a form change proposed by what the pet did, promoted by a human) uses the house's promotion rule: a model describes, a harness judges, a human promotes; nothing changes a weight silently.
**What this means for the order of work:** (1) needs core and body types as data, BUILT as a proof of concept below; (2) the world and the verbs (walk, give, plant, water, harvest), the `hai_world` op is the start; (3) forms as an evolution tree over body types (`tree_lint` checks the tree); (4) the deep anatomy layer, optional; (5) the zoom ladder, last.

## 10. Proof of concept (BUILT and run 2026-11-23): `ops/hai_pet.c`, case `hai_pet`
**What it is:** a C op, one ledger, three body types from data (`pet/data/body_organic.pdl`, `body_robot.pdl`, `body_cyborg.pdl`, the same row shapes as the house `needs.pdl` and `itemdata.pdl`: `RATE|need|points|per_minutes`, `USE|item|verb|need|delta`). Verbs: `born`, `give`, `tick`, `use`, `weight` (tenths, 0 turns a need off, 40 is four times as fast), `status`. Everything (needs, the carried sub-point remainder, weights, inventory) is whatever replaying the rows gives.
**Run by hand (observed):** four hours on the shipped data: organic `hunger=40`; robot `drain=32 heat=16`; cyborg `hunger=24 drain=20`. A robot refused an apple ("this body cannot use that item"); a cyborg refused a cell it did not hold; an apple lowered hunger by 40 and was burned; `weight hunger 0` kept hunger at 0 through ten more hours.
**The check (case `hai_pet`, 34 checks, all pass):** the real needs op `survivor_op` is the ORACLE for the tick arithmetic. Both are run on the same minutes against the same odd rate (7 points per 45 minutes): ten 10-minute ticks then 1 minute gives `hunger=15`, then 37 more gives 21, then 1000 more clamps at 100, on both; this proves the remainder carry matches the house rule. Then the three bodies, items, weights, refusals as rows, and a hand-edited ledger whose rule-breaking rows are skipped on replay.
**Mutants that turn it red (run):** dropping the remainder (2 checks fail), ignoring weights (2), letting any item work on any body (4), clamping at 120 (1). The unmodified source passes all 34.
**NOT proven (do not claim):** eating through the item ledger (`survivor_op eat` is not compared; the pet holds a plain count), the world or walking, farming, anatomy parts, evolution or forms, MP, a JS port, the web page, the window, any video. Body data is read at replay time, so editing a body file changes how an old ledger replays; a data hash row (as the house rulesets have) is the fix and is NOT done. This is a proof of concept of the needs core and of "a body type is data", nothing more.
